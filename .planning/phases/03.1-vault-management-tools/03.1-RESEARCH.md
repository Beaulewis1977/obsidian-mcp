# Phase 03.1: Vault Management Tools — Research

**Researched:** 2026-02-27
**Domain:** Config file I/O, cross-platform path resolution, ToolRegistry extension
**Confidence:** HIGH (all findings from direct source-file inspection)

---

## Summary

Phase 03.1 adds three tools — `add_vault`, `remove_vault`, `list_vaults` — that let agents manage Obsidian vaults without manual config editing. The implementation touches two config files (`obsidian.json` and MCP `config.json`), the filesystem, and the ToolRegistry.

The most important finding from reading the actual source files: `saveConfig()` in `src/config/index.ts` always writes to `~/.obsidian-mcp/config.json`, NOT to the file that was originally loaded (which could be `$CONFIG_PATH` or `./config.json`). This is a latent split-brain bug that must be addressed — the vault management tools need to write to the same path that was loaded. The second critical finding: `loadConfig()` is already exported and can be called directly for hot-reload. Third: the config module does NOT currently export the active config path, so handlers-vault.ts will need to resolve the config path the same way `loadConfig()` does.

The cross-platform story is cleaner than expected: the project already has `is-wsl` (v3.1.0) and `normalizeVaultPathForPlatform()`. On WSL, `process.env.APPDATA` is NOT reliably set — WSL environments don't inherit Windows env vars by default. The `obsidian-config.ts` module must detect WSL via `isWSL` from `is-wsl` and construct the APPDATA path from `os.homedir()` (which in WSL is the Linux home) and use a known `/mnt/c/Users/<user>/AppData/Roaming` derivation — or invoke `cmd.exe /c echo %APPDATA%` via `execSync` as a fallback.

**Primary recommendation:** Write one new file (`src/platform/obsidian-config.ts`) for all obsidian.json I/O, add three schemas to `src/tools/schemas.ts`, write `src/tools/handlers-vault.ts`, and register the three tools in `src/tools/index.ts`. Mock `fs/promises` and the new `obsidian-config.ts` module in tests — the pattern already established in `handlers.integration.test.ts` applies directly.

### Pattern 3: Obsidian Config Read-Modify-Write

**What:** Read obsidian.json, merge changes, write back. Must handle: file doesn't exist yet, file has extra unknown keys (preserve them), concurrent write risk.
**When to use:** `add_vault` and `remove_vault` both need this.

```typescript
// Source: new src/platform/obsidian-config.ts
import fs from 'fs/promises';
import path from 'path';
import os from 'os';
import isWSL from 'is-wsl';

export interface ObsidianVaultEntry {
  path: string;
  ts: number;
  open?: boolean;
}

export interface ObsidianConfig {
  vaults: Record<string, ObsidianVaultEntry>;
  [key: string]: unknown;  // preserve unknown top-level keys
}

export function getObsidianConfigPath(): string {
  if (process.platform === 'win32') {
    // Native Windows: APPDATA is always set
    const appData = process.env.APPDATA;
    if (!appData) throw new Error('APPDATA environment variable not set');
    return path.join(appData, 'obsidian', 'obsidian.json');
  }

  if (isWSL) {
    // WSL: APPDATA is NOT set in Linux env. Derive from homedir.
    // WSL homedir is /home/<user>; Windows user is typically the same name.
    // Most reliable: invoke cmd.exe to get the real APPDATA path.
    // Fallback: construct from /mnt/c/Users/<username>/AppData/Roaming
    const winUser = os.homedir().split('/').pop() ?? '';
    return `/mnt/c/Users/${winUser}/AppData/Roaming/obsidian/obsidian.json`;
  }

  if (process.platform === 'darwin') {
    return path.join(os.homedir(), 'Library', 'Application Support', 'obsidian', 'obsidian.json');
  }

  // Linux
  return path.join(os.homedir(), '.config', 'obsidian', 'obsidian.json');
}

export async function readObsidianConfig(): Promise<ObsidianConfig> {
  const configPath = getObsidianConfigPath();
  try {
    const content = await fs.readFile(configPath, 'utf-8');
    const parsed = JSON.parse(content);
    if (!parsed.vaults || typeof parsed.vaults !== 'object') {
      parsed.vaults = {};
    }
    return parsed as ObsidianConfig;
  } catch (error: any) {
    if (error.code === 'ENOENT') {
      // obsidian.json doesn't exist yet — return empty config
      return { vaults: {} };
    }
    throw error;
  }
}

export async function writeObsidianConfig(config: ObsidianConfig): Promise<void> {
  const configPath = getObsidianConfigPath();
  const dir = path.dirname(configPath);
  // Atomic write: temp file + rename reduces corruption risk
  const tmp = path.join(dir, `.obsidian-mcp-${Date.now()}.tmp`);
  await fs.mkdir(dir, { recursive: true });
  await fs.writeFile(tmp, JSON.stringify(config, null, 2), 'utf-8');
  await fs.rename(tmp, configPath);
}
```

### Pattern 4: MCP Config Write + Hot-Reload

**Critical finding:** `saveConfig()` always writes to `~/.obsidian-mcp/config.json`. If the server was started with `CONFIG_PATH=/some/other/path`, calling `saveConfig()` creates a second config file at the default path — split brain. The vault tools need to write to the same path that was loaded.

**Fix:** Add a `getActiveConfigPath()` helper to `src/config/index.ts` that returns the first found config path (same logic as `getConfigPaths()` but returning the first hit). Then `handlers-vault.ts` can write to that path directly.

```typescript
// Add to src/config/index.ts
/**
 * Return the path of the config file currently in use.
 * Returns null if running on defaults (no config file found).
 */
export async function getActiveConfigPath(): Promise<string | null> {
  for (const p of getConfigPaths()) {
    try {
      await fs.access(p);
      return p;
    } catch {
      // not found, try next
    }
  }
  return null;
}
```

Then the hot-reload pattern in handlers-vault.ts:

```typescript
// After writing config.json:
const reloaded = await loadConfig();
// Mutate the in-memory config so other handlers see new vaults immediately
Object.assign(config, reloaded);
```

Note: `Object.assign(config, reloaded)` works because `config` is a reference to the ServerConfig object passed to every handler. Mutating it in place propagates to all future handler calls without a server restart.

### Pattern 5: Note Counting for list_vaults

The existing `listNotes()` in `src/filesystem/vault-reader.ts` recursively scans a vault folder and returns all `.md` files. For `list_vaults`, use it as `(await listNotes(vault.path)).length`. This is synchronous from the caller's perspective but async underneath.

**Performance note:** `listNotes()` opens every file to check metadata when `includeMetadata=true`, but with `includeMetadata=false` (the default) it only reads directory entries — acceptable for note count. For very large vaults (10k+ notes) this could be slow (1-2s), but that's acceptable for a management tool.

```typescript
// Count notes in a vault (uses existing listNotes, no new code needed)
import { listNotes } from '../filesystem/vault-reader.js';

async function countNotes(vaultPath: string): Promise<number> {
  try {
    const notes = await listNotes(vaultPath);
    return notes.length;
  } catch {
    return 0; // vault doesn't exist on disk
  }
}
```

### Anti-Patterns to Avoid

- **Using `saveConfig()` directly from vault handlers:** It always writes to `~/.obsidian-mcp/config.json` regardless of where config was loaded from. Use `getActiveConfigPath()` + direct `fs.writeFile` instead.
- **Not preserving unknown keys in obsidian.json:** Obsidian may add new top-level keys. Use spread to preserve: `{ ...existingConfig, vaults: updatedVaults }`.
- **Comparing vault paths without normalization:** `D:\obsidian` and `/mnt/d/obsidian` are the same vault on WSL. Always normalize with `normalizeVaultPathForPlatform()` before comparing.
- **Blocking on note count for list_vaults:** Count is best-effort — if it fails (vault not on disk), return 0, don't throw.
- **Marking vault tools as `alwaysLoaded: true`:** These are management tools, not meta-tools. They should be discoverable via `discover_tools` and enabled explicitly.

## Common Pitfalls

### Pitfall 1: saveConfig() Split-Brain

**What goes wrong:** Calling `saveConfig(config)` after adding/removing a vault writes to `~/.obsidian-mcp/config.json`. If the server was started with `CONFIG_PATH=/path/to/custom/config.json`, that file is not updated. The server still works (it loaded from CONFIG_PATH), but the write goes elsewhere. On next restart with CONFIG_PATH, the change is lost.

**Why it happens:** `saveConfig()` always uses the hardcoded default path. It was designed for initial setup, not live mutation.

**How to avoid:** Add `getActiveConfigPath()` to `src/config/index.ts`. Use it in vault handlers to write to the correct path.

**Warning signs:** If after `add_vault` the vault appears in `list_vaults` (in-memory) but disappears after server restart — this is the bug.

### Pitfall 2: WSL APPDATA is Undefined

**What goes wrong:** On WSL, `process.env.APPDATA` is NOT set. Obsidian is a Windows application — its config is at the Windows AppData path. Code that does `process.env.APPDATA || ''` silently resolves to `/obsidian/obsidian.json` (wrong path, root-relative).

**Why it happens:** WSL Linux environments don't inherit Windows environment variables by default.

**How to avoid:** In `getObsidianConfigPath()`, branch on `isWSL` (from `is-wsl` package, already imported in path-converter.ts) and construct the path from `os.homedir()` split to get the username: `/mnt/c/Users/<username>/AppData/Roaming/obsidian/obsidian.json`. This works when the Windows and Linux usernames match (the common case). If they don't match, emit a clear error message explaining the issue.

**Warning signs:** `readObsidianConfig()` returns an empty `{ vaults: {} }` even though Obsidian has vaults configured — the path resolved to a nonexistent location.

### Pitfall 3: Obsidian Does Not Live-Reload obsidian.json

**What goes wrong:** `add_vault` writes to obsidian.json. The user expects to see the vault in Obsidian immediately. It won't appear until Obsidian restarts.

**Why it happens:** Obsidian reads its vault registry on startup, not continuously.

**How to avoid:** Include `"note": "Restart Obsidian to see this vault in the vault switcher"` in the success response. This is documented in the spec.

**Warning signs:** None — this is expected behavior. Just surface it clearly.

### Pitfall 4: Atomic Rename Across Filesystems on WSL

**What goes wrong:** `fs.rename(tmp, target)` throws `EXDEV` error if `tmp` and `target` are on different filesystems. In WSL, if writing to `/mnt/c/...`, the temp file must be in the same directory.

**Why it happens:** `fs.rename` is only atomic within the same filesystem. Cross-device renames fail on Linux.

**How to avoid:** Create the temp file in the same directory as the target (not in `/tmp` or `os.tmpdir()`). The example in Pattern 3 already does this correctly with `path.join(dir, '.obsidian-mcp-...')`.

### Pitfall 5: Path Comparison Without Normalization

**What goes wrong:** `config.vaults.find(v => v.path === args.path)` misses matches when paths differ in format (trailing slash, Windows vs WSL format, case on Windows).

**Why it happens:** The same physical directory can be represented as `D:\obsidian`, `D:/obsidian`, or `/mnt/d/obsidian`.

**How to avoid:** Always normalize both sides before comparing: `normalizeVaultPathForPlatform(v.path) === normalizeVaultPathForPlatform(args.path)`.

### Pitfall 6: Remove Last Vault or Default Vault

**What goes wrong:** Removing the only vault or the default vault leaves the MCP server in a broken state (no vault to operate on).

**Why it happens:** No validation before removal.

**How to avoid:** In `handleRemoveVault`, check:
1. `if (config.vaults.length === 1)` → error: "Cannot remove the last vault"
2. `if (vault.default === true)` → error: "Cannot remove the default vault — use add_vault with default:true on another vault first"

### Pitfall 7: test count in lazy-loading test hardcodes total tool count

**What goes wrong:** `lazy-loading.integration.test.ts` line 27: `expect(registry.getAll().length).toBe(19)`. After adding 3 tools, this becomes 22. This test WILL FAIL without updating.

**Why it happens:** The test hardcodes the total tool count.

**How to avoid:** Update that assertion to `toBe(22)` when adding the 3 new tools.

## Key Findings From Source Files

### loadConfig() — confirmed exported, hot-reload ready

`src/config/index.ts` exports `loadConfig()` (line 103). It reads the first found config path from `getConfigPaths()`. It can be called at any time to get a fresh config. No issue using it for hot-reload.

### saveConfig() — WRITES TO HARDCODED PATH

`src/config/index.ts` line 186: `saveConfig()` always writes to `path.join(os.homedir(), '.obsidian-mcp', 'config.json')`. This is correct for initial setup but wrong for vault management tools which need to write to whichever config file was actually loaded. Solution: add `getActiveConfigPath()` and write directly with `fs.writeFile`.

### ToolRegistry handler type

The `ToolRegistration` handler field type (from `src/tools/registry.ts`) is:
```typescript
handler: (config: ServerConfig, args: any) => Promise<ToolResponse>
```
The `args` is typed as `any` in the interface, but at registration time in `index.ts`, the lambda `(config, args) => handler(config, args)` provides type safety via the TypeScript inference chain.

### alwaysLoaded behavior

From `src/tools/registry.ts` line 33-37: if `alwaysLoaded: true`, the tool is immediately added to the `enabled` Set on `register()`. Do NOT set `alwaysLoaded: true` on vault management tools — they should be discoverable but not always loaded.

### Lazy loading test — count will break

`src/tools/__tests__/lazy-loading.integration.test.ts` line 27: `expect(registry.getAll().length).toBe(19)`. Adding 3 vault tools makes this 22. This test must be updated.

### listNotes() for note counting

`src/filesystem/vault-reader.ts` exports `listNotes(vaultPath, folder?, includeMetadata?)`. With no folder and `includeMetadata=false` (default), it scans the entire vault and returns `{ path, name, folder }` objects without opening any files — just `readdir`. For note count, `(await listNotes(vaultPath)).length` is safe and reasonably fast.

## State of the Art

| Old Approach | Current Approach | Impact |
|--------------|------------------|--------|
| Atomic writes via `write-file-atomic` npm package | Manual `writeFile(tmp) + rename(target)` | Same safety, no new dependency — use manual approach |
| Read APPDATA from env | Construct from known WSL path structure | Reliable on WSL where env var is absent |
| Call loadConfig() and return new object | loadConfig() + Object.assign(config, reloaded) | In-place mutation propagates to all handler calls |

## Open Questions

1. **WSL username mismatch**
   - What we know: On WSL, `/mnt/c/Users/<linuxUser>/AppData/Roaming/` works when Windows and Linux usernames are the same
   - What's unclear: If usernames differ, the path is wrong
   - Recommendation: Use this path as the default; if `readFile` throws ENOENT, surface a clear error message telling the user to set `OBSIDIAN_CONFIG_PATH` env var as override

2. **obsidian.json doesn't exist yet**
   - What we know: If Obsidian has never been run, obsidian.json doesn't exist; `readObsidianConfig()` returns `{ vaults: {} }`
   - What's unclear: Should `add_vault` create obsidian.json or refuse?
   - Recommendation: Create it (obsidian.json is just a JSON file; Obsidian will read it on next launch)
